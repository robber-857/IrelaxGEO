# Irelax AU 实施步骤与后台操作手册

日期：2026-10-19。本文是执行手册，所列改动尚未执行。后台菜单名称以实际版本、许可和权限为准。

## 1 现在从后台开始做什么

你已登录 Dashboard，下一步优先进行以下只读盘点。不要将截图中的更新通知当作本轮整改的开始按钮。

| 顺序 | 建议入口 | 查看并记录 | 用途 |
|---|---|---|---|
| 1 | WooCommerce → Status | WordPress、WooCommerce、PHP、主题版本、模板覆盖及环境告警 | 确定技术基线；共享前去除路径等敏感字段 |
| 2 | Plugins → Installed Plugins | Rank Math 免费/Pro、缓存、Schema、品牌 taxonomy、评论、页面构建器、备份和支付插件的版本及启用状态 | 找到数据输出源和升级依赖 |
| 3 | Appearance / Flatsome | 当前主题、子主题、许可提示；现有 Header、UX Blocks 和页面模板 | 判断应该改设置、内容还是模板 |
| 4 | Rank Math → Dashboard、Titles & Meta、Local SEO 等实际入口 | Schema/WooCommerce 模块、Products 品牌设置、默认 Schema、机构信息 | 检查是否支持报告建议的映射 |
| 5 | WPCode / 现有代码片段管理器 | FAQ、Product、Organization、hreflang、VideoObject 相关片段及作用范围 | 防止重复注入和全局误改 |
| 6 | Pages → FAQ、Home、About、Showrooms | 页面 ID、使用的编辑器、模板、FAQ 区块与单页 Schema | 查明事实和标记来自哪里 |
| 7 | Products → Biovis、Healer X | 商品类型、品牌分类、SKU、变体、短描述、规格属性和单页 Schema | 确定字段映射，保留原值 |
| 8 | 主机后台及已有备份工具 | 文件和数据库备份、恢复方式、测试环境、缓存层 | 管理员登录不等于具备主机恢复能力 |

完成后产出一份环境清单、页面 ID 对照表、Schema 来源图和第一批变更单。当前尚未连接用户已登录的 Edge 会话，上述入口均是待核实路线。

## 2 建立可恢复的实施环境

1. 记录线上版本和最近变更；导出现有 SEO 设置、代码片段及本批页面原内容。
2. 由已有主机/备份设施创建文件和数据库备份，记录时间和恢复路径。在测试环境验证恢复后的关键页面可访问。
3. 使用已有 staging，或由主机管理员建立测试副本。测试副本应限制访问、禁止索引，隔离真实付款、邮件、订单 webhook 和生产集成；尽量不复制无关客户数据。
4. 确认部署方式：页面和配置逐项迁移，代码按版本部署。不得直接用旧测试库覆盖生产库，以免丢失新订单和客户变更。
5. 先处理阻碍恢复或修改的运行问题。主题注册失败需找账号/许可负责人核实；WordPress 和插件升级放入单独维护批次。

进入下一步的条件：问题可复现、改动点可定位、业务值有来源、存在恢复方案。

## 3 第一批修复 FAQ 和产品数据

### 3.1 FAQ

1. 获取首页和 FAQ 页的原始 HTML，枚举全部 JSON-LD 块，逐块解析；记录失败块和来源。
2. 在页面内容、Rank Math 和 WPCode 中定位对应生成源。不能因为插件名字相关就停用整个插件。
3. 将 FAQ 内容维护在一个可信来源中；生成 JSON 时使用标准编码器，正确转义换行和引号。
4. 核对每个 Question 和 Answer 与可见页面：保留真实问答；首页只在业务确实需要时添加可见 FAQ，或清理不对应可见内容的标记。
5. 涉及保修和退款的答案先等待 R04 业务确认，不能复制报告中的三年保修示例。
6. 测试折叠组件、原始 HTML 内容和 JSON 解析。FAQ 不以 Google 富结果出现为验收要求。

### 3.2 产品品牌与标识

1. 在 Biovis、Healer X 确认真实商品类型、品牌 taxonomy 和字段来源；记录原 SKU 与变体关系。
2. 检查 Rank Math 当前版本是否支持从现有品牌分类映射。可用时先在测试环境设置；不可用时采用有明确范围的过滤器或小插件，不额外叠加一套完整 Product Schema。
3. `brand` 填制造商品牌，`seller` 对应零售商；产品 `name` 用真实商品名，浏览器 SEO 标题可保留站点后缀。
4. SKU 沿用库存系统；有依据时补 MPN/GTIN，不推测编码。保留实际 ProductGroup、hasVariant、Offer 等关系，不因添加字段拆坏变体。
5. 比较原始 HTML 中 name、brand、标识、价格、AUD 币种、库存与可见商品选项。
6. 两个样板通过后，按真实在售数量和商品类型扩大检查；报告中的 47 个商品不是当前数量的确认值。

### 3.3 规格和面包屑

1. 向业务获取 Healer X 气囊数的厂商依据，确认 32/34 是否来自不同版本或统计口径。
2. 同步短描述、属性、规格表、图片文字说明和 Schema；图片无法当批替换时，明确记录未完成项，不宣称冲突已清零。
3. 确认分类最终 URL，修正可见面包屑及 BreadcrumbList 的来源。优先改内部引用，不批量修改商品 URL。
4. 复查价格、库存、加购、购物车、结账入口、搜索和移动导航。

第一批完成交付：变更明细、改前改后 HTML、JSON 解析结果、字段对照、界面截图及回滚操作。未有正确业务值的条目保持阻塞状态，其他独立条目可继续。

## 4 第二批补产品内容和门店信息

1. 为两款样板产品建立可见的 At a Glance 模块：品牌、型号、已核实规格、适用条件、价格来源及政策链接。价格尽量由商品数据动态生成。
2. 提取信息图中的关键卖点，改写成有来源的正文。优先形成清晰的短介绍、参数表和按主题分组的说明，不机械重复每张图片。
3. 信息图 alt 描述核心内容，完整技术参数放正文；装饰图片保留空 alt。检查手机阅读与原始 HTML。
4. 用已确认的品牌事实修正首页和 About。没有来源的“第一”“唯一”“最大”不替换成另一条未经证明的宣传。
5. 建立门店主表：营业状态、官方店名、地址、电话、营业时间、坐标、页面、图片及负责人；区分自营门店与合作展示点。
6. 由主表生成一致的页面和 Store 信息，维护稳定 ID。报告中的六家为候选核实清单，不能假定目前全部在营业。
7. 清理错误 Article、admin 预发域名 sameAs 及导航标题污染；保持导航交互和视觉布局可用。
8. 调查评论重复与计数差异，统一数据源和口径；不批量删除评论。

## 5 第三批技术治理与跨站协调

### AU 站内

- sitemap：确认规范 URL、索引策略、分页覆盖和时间生成机制，再处理缓存或生成器。真实业务相关商品保留正常策略。
- robots：保留管理目录等必要限制。自定义 UA 的 200 响应仅是一次抓取结果，不证明真实搜索爬虫一定可访问。
- llms.txt：复现 500 后追踪路由或服务器错误；需要维护时提供有效内容，否则按正常缺失资源处理。不是上线首批阻塞项。
- 中文页面：检查实际内容及最终 URL，再配置语言和英文对应关系。不能直接采用报告中互有差异的中文首页路径。
- URL：仅迁移确认有问题的地址，准备旧新映射和回归；优先修正内部链接，避免为了统一格式改动所有已收录页面。
- 视频：需要时从真实视频元数据服务端输出；检查与现有 JS 注入是否重复。
- 内容：导购补实际比较表、价格日期、来源和作者身份；品牌拼写统一不改变域名和社交账号。

### AU 与 NZ

1. 确认两站法律及品牌关系、NZ 负责人和本次允许修改范围。
2. 选择 Organization 模型，列出两站所有被引用的实体 ID，评估迁移影响。
3. 建立真正等价页面的配对表，不按相同 slug 自动配对。
4. 两端同时验收 hreflang、自引用及 canonical；各地区价格、货币、门店和政策仍各自正确。
5. NZ 不能同步时记录依赖，先推进 AU 独立整改，不宣称跨站项目已完成。

## 6 分批发布与回滚

发布前：明确本批 URL、页面 ID、代码文件和配置项；业务文案完成确认；测试环境验收完成；保存最新生产备份及字段原值。检查近期生产内容变化，避免覆盖他人更新。

发布时：按批准的具体批次迁移改动；确认真实存在的缓存层，再按需清理相关缓存；记录操作者、时间和版本。内容、Schema 与平台升级分别发布，便于定位问题。

发布后：使用未登录视角查看桌面和手机页面；抓取原始 HTML 解析；核对 JSON-LD 与可见内容；确认商品选项、加入购物车、数量、金额和结账入口。测试中不要向真实客户发送通知，不提交真实付款。预约或支付需要单独测试方案时保留未验证状态。

回滚触发：新增 5xx、核心页面不可访问、加购或结账入口阻断、价格库存误变、全站 Schema 重复冲突，或影响客户使用的明显布局故障。

回滚方式：先撤回本批代码或恢复具体设置/页面版本，并刷新相关缓存；验证问题消失。涉及数据库时由主机负责人选择不会覆盖新订单的恢复方式；不要把整库恢复作为普通文案改动的默认操作。

## 7 完成定义

某项任务只有“修改记录 + 结果证据 + 对应验收通过”齐全才标为完成。后台显示保存成功、缓存已清理或插件已更新都不能单独作为完成证据。

实施结束交付：已验收需求列表、仍阻塞项和原因、业务事实表、URL 对照、代码版本或配置导出、发布与回滚记录、下一轮监测日期。搜索收录和 AI 引用变化应在观察期结束后单独报告。
